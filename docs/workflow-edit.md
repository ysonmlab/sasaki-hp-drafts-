# workflow-edit.md

Task: 既存ページ（`{page-name}`）のコード改善 を開始します。

新規作成の [workflow-coding.md](workflow-coding.md) が「ゼロから書く」フローなのに対し、
このドキュメントは **すでにある HTML / CSS を安全に直す** ためのフロー。
以下の3タイプの改善を対象とする。

- **A. レスポンシブ対応**（SP / PC の崩れ・未対応を整える）
- **B. コード整理**（HTML / CSS のリファクタ・重複排除・命名統一）
- **C. レイアウト崩れ修正**（はみ出し・ずれ・固定要素の不具合など）

## 2つのモード

改善の広さで進め方が変わる。まずどちらかを決める。

- **単ページ改善**（既定）… 対象を **1ページ / 1セクション**に限定して直す。
  → このまま下の「事前確認 → Task 1〜4」を進める。
- **サイト全体改善** … 全ページ横断で直す（例：サイト全体をレスポンシブ対応）。
  → 一括では行わず **共通先行 → ページ順次** に分解する。
  詳細は末尾の [サイト全体モード](#サイト全体モード共通先行--ページ順次) を参照。中身は単ページ改善の反復。

> このキットの最優先ルール（[claude/CLAUDE.md](../claude/CLAUDE.md) 絶対ルール）：
> **指示されたセクション以外のコードは、リファクタリング目的であっても勝手に変更しない。**
> 既存改善では特にこの「不変性」を守り、**触ってよい範囲を最初に確定**してから作業する。

---

## 事前確認（作業前に必ず決める）

作業を始める前に、以下を依頼者に確認する（不明なら質問する。勝手に広げない）。

- **対象ページ**：どの HTML / CSS ファイルか（例：`about.html` / `assets/css/about.css`）
- **対象範囲**：ページ全体か、特定セクション（`sect-*`）のみか
- **改善タイプ**：A / B / C のどれか（複数可）
- **崩れの再現条件**（Cの場合）：どの画面幅・どのブラウザ・どの操作で起きるか
- **見た目の維持 or 変更**：既存の見た目を保ったまま直すのか、デザイン自体を変えるのか

> 確認が取れるまでコードは書かない。範囲外には触れない。

---

## Task 1: Explore（現状把握）

以下を読んで、既存の構造とルールを理解する。**この段階ではコードを書かない。**

- [claude/CLAUDE.md](../claude/CLAUDE.md)（命名・絶対ルール・設計思想）
- 対象の `{page-name}.html` と `assets/css/{page-name}.css`（現状のコード）
- `assets/css/common.css`（既存の共通トークン・共通パーツ。再利用先／競合源の把握）
- [docs/css-architecture.md](css-architecture.md)（reset / common / ページ固有の責務と読み込み順）
- [docs/css-gotchas.md](css-gotchas.md)（崩れ・固定要素・レスポンシブの典型的な落とし穴）
- [claude/skills/layout-system/SKILL.md](../claude/skills/layout-system/SKILL.md)（レイアウト判定）
- [logs/PATTERNS.md](../logs/PATTERNS.md)（この案件で既知の注意点・過去の修正理由）

把握すること：

- 対象セクションが `.pg-{page} .sect-*` スコープを守れているか
- common.css で賄える／すでにある部品を、ページ固有CSSで重複再定義していないか
- 崩れ・未対応の原因が **どのレイヤー（reset / common / ページ固有）** にあるか

完了後、Task 2 に進む。

---

## Task 2: Plan（改善計画）

修正前に、**何を・どこまで・どう直すか**を整理して依頼者に共有する。
既存改善では「変更点」と「変更しない点」を明示することが重要。

    target: {page-name}.html / assets/css/{page-name}.css
    scope: sect-{section-name}（この範囲のみ）
    type: A(レスポンシブ) / B(整理) / C(崩れ修正)

    現状の問題:
    - 例）PC幅で hero が2カラムにならず縦積みのまま
    - 例）約400px以下で container が横スクロールする

    原因（推定）:
    - 例）media query が未記述
    - 例）子要素に width:100vw を使用（css-gotchas #4）

    修正方針:
    - 例）SP→PC の順で media query を追加し PC で grid 2カラム化
    - 例）100vw を 100% に置換

    変更しない範囲:
    - 例）ヘッダー / フッター / 他セクションには触れない

改善タイプ別の着眼点：

- **A. レスポンシブ** … media query は **SP → PC** の順。ブレークポイントを既存と揃える。
  固定 px を避け、`%` / `fr` / `clamp()` / `min()` などで可変にできないか検討する。
- **B. 整理** … common に出すべき共通パーツと、ページ固有に残すべき装飾を切り分ける。
  重複セレクタ・未使用CSS・冗長な `div`・詳細度の競合を洗い出す。**挙動と見た目は変えない**。
- **C. 崩れ修正** … まず [docs/css-gotchas.md](css-gotchas.md) の該当項目を疑う
  （`100vw` はみ出し／`position:fixed` の包含ブロック／`overflow:hidden` 下の `sticky` 等）。

完了後、Task 3 に進む。

---

## Task 3: Edit（修正実装）

計画した範囲だけを最小差分で修正する。

- 変更は **対象スコープ内（`.pg-{page} .sect-*` / 対象HTMLの該当セクション）** に閉じる
- 共通の直しは common.css、そのページだけの直しはページ固有CSSへ（[css-architecture.md](css-architecture.md)）
- media query は **SP → PC** の順を維持する
- HTML構造を変える場合も、意味（semantic）・見出し階層・`alt`・`loading="lazy"` を保つ
- **float 禁止**・**外部フレームワーク禁止**（Vanilla CSS）は既存改善でも同じ

### タイプ別の注意

- **A. レスポンシブ**：既存の PC 用スタイルを SP に漏らさない／その逆も防ぐ。
  既存ブレークポイントと不一致な値を新規に増やさない。
- **B. 整理**：**見た目を1pxも変えない**のが原則。共通化でスコープを広げる場合は
  影響範囲（他ページ）を必ず確認してから common.css へ移す。判断に迷えば依頼者に確認。
- **C. 崩れ修正**：対症療法でなく原因レイヤーを直す。`!important` での握りつぶしは避け、
  詳細度・読み込み順で解決する。

---

## 検証（確認）

修正したページを表示確認する。

- ルート直下の `{page-name}.html` をブラウザで直接開く（ダブルクリック／`file://`）。
- **SP / PC 両方**を確認する（DevTools のデバイスモード `Ctrl+Shift+M`、幅を狭める）。
  - 特に A・C では、狭い幅（~360px）〜広い幅まで連続的に動かして崩れが無いか見る。
- **B（整理）では回帰確認を重点的に**：修正前後で見た目が変わっていないか、
  他セクション・他ページに影響が出ていないかを確認する。
- 崩れ・固定要素・レスポンシブ切替の確認時は [docs/css-gotchas.md](css-gotchas.md) を参照する。

完了後、Task 4 に進む。

---

## Task 4: Record（記録）

- 修正内容（何を・なぜ直したか）→ [logs/CHANGELOG.md](../logs/CHANGELOG.md)
- 遭遇したエラーと解決策 → [logs/ERRORLOG.md](../logs/ERRORLOG.md)
- 崩れの原因と再発防止の知見 → [logs/PATTERNS.md](../logs/PATTERNS.md)

依頼者から追加の指摘を受けた場合：

- 同じミスを防ぐルールを [logs/PATTERNS.md](../logs/PATTERNS.md) に記録する
- 横断的に効く知見なら [docs/css-gotchas.md](css-gotchas.md) への追記を提案する
- 必要なら [claude/CLAUDE.md](../claude/CLAUDE.md) 更新を提案する

最後に：

`Task: {page-name} ページのコード改善 → 完了`

と報告する。

## サイト全体モード（共通先行 → ページ順次）

「サイト全体をレスポンシブ対応したい」「サイト全体のコードを整理したい」のように
**全ページ横断**で直す場合のモード。**改善タイプ A / B / C いずれにも使える**（複数同時も可）。

**全ページを1セッションで一括修正しない。** 影響範囲が読み切れず切り分けが不能になり、
非エンジニア保守の方針にも反する。代わりに以下の4ステップに分解する。
各ページの実作業は、上の単ページ改善（Task 1〜4）を**1ページ分の単位として反復**するだけ。

> **タイプ別の全体像**
> - **A. レスポンシブ** … ブレークポイント統一 → 共通部の崩れ → 各ページの崩れ
> - **B. コード整理** … common.css の重複排除・命名統一・共通パーツ集約 → 各ページ固有CSSの整理
> - **C. 崩れ修正** … 共通部（header/footer/nav）の崩れ → 各ページ固有の崩れ
>
> どのタイプも「**共通(common)を先に固める → ページを順次**」という骨組みは同じ。

### ステップ1. 棚卸し（Inventory）

まず全体像を把握する。**この段階では修正しない。**

- ルート直下の対象 HTML 一覧（`index.html` / `about.html` …）を列挙する
- 全ページ共通の部品（ヘッダー / フッター / グローバルナビ）を特定する
- タイプ別に現状の問題を洗い出す：
  - **A. レスポンシブ** … 現状のブレークポイント（`common.css` / 各ページCSS）のバラつき、
    **ページ × 画面幅**でどこが崩れる／未対応か（例：`about` の hero が ~768px で崩れる）
  - **B. コード整理** … common と各ページで重複しているセレクタ、未使用CSS、命名のゆれ
    （`sect-*` 命名規則からの逸脱）、冗長な `div`、詳細度の競合箇所
  - **C. 崩れ修正** … 崩れの再現条件（ページ・画面幅・操作）と、原因が共通部かページ固有かの当たり

### ステップ2. 共通方針の確定（common 先行パス）

全ページに効く土台（`assets/css/common.css`）を先に固める。ここだけは意図的に全ページへ影響させる。
タイプ別に行うこと：

- **A. レスポンシブ** … **ブレークポイントを1つに統一**（`SP → PC` の順は維持）。
  共通のヘッダー / フッター / グローバルナビの崩れを common で **一度だけ**直す。
- **B. コード整理** … common の重複セレクタ・未使用CSSを整理し、**命名を規則に統一**する。
  複数ページで使う部品（ボタン・カード等）を common に集約する。**見た目は変えない**のが原則。
  共通化でスコープを広げる場合は、波及先の全ページを確認してから移す。
- **C. 崩れ修正** … 共通部（header/footer/nav）が原因の崩れを common で直す。

- どのタイプも、common を変えると全ページに波及するため、**複数ページを開いて表示確認**してから次へ進む

> どこを common で直し、どこをページ固有に残すかは [css-architecture.md](css-architecture.md) の責務表に従う。

### ステップ3. ページ順次パス（1セッション1ページ）

共通が固まったら、各ページを **1セッション1ページ**で順に対応する。

- 各ページの作業は、上の **Task 1〜4** をそのまま実施する（対象を1ページに固定）
- ページ固有の対応（崩れ・整理とも）は `.pg-{page} .sect-*` スコープ内で行う（**common には戻さない**）
- 依頼は下の単ページ用テンプレートを、対象ページを差し替えて使う
- セッションを分ける理由 → [how-to-use.md](how-to-use.md) と同じ（情報量を抑え影響を局所化する）

### ステップ4. 進捗管理

セッションをまたいでも続きから進められるよう、対応状況を記録する。

- 対応済み / 未対応ページのチェックリストを [logs/CHANGELOG.md](../logs/CHANGELOG.md) に残す

  ```
  ## サイト全体改善（進捗）※タイプは A/B/C など案件に合わせて記す
  - [x] common（レスポンシブ:ブレークポイント統一・整理:重複排除/命名統一・header/footer/nav）
  - [x] index.html
  - [ ] about.html
  - [ ] contact.html
  ```

- 横断的に効いた知見（崩れの原因・整理の判断基準など）は
  [logs/PATTERNS.md](../logs/PATTERNS.md) / [css-gotchas.md](css-gotchas.md) に残す

### サイト全体モードの注意点

- **一度に全ページを書き換えない。** common 先行 → ページ順次の順序を守る。
- スコープが全ページに広がるのは **common を触るステップ2のみ**。それ以外はページスコープに閉じる原則は不変。
- ブレークポイントを新たに乱立させない（統一値を各ページで使い回す）。

## 依頼テンプレート（コピペ用）

### 単ページ改善用

新しいセッションで、以下を埋めて貼り付けると開始できる。

```
プロジェクト名：{project-name}
対象ページ：{page-name}（例 about.html / assets/css/about.css）
対象範囲：{セクション or ページ全体}（例 sect-about-hero のみ）
改善タイプ：A レスポンシブ / B コード整理 / C 崩れ修正（複数可）
補足：{崩れの再現条件・維持したい見た目など}

Task: 既存ページのコード改善を開始します。
docs/workflow-edit.md を読んで進めてください。
指示した範囲以外は変更しないでください。
```

### サイト全体改善用（2段構え）

**① まず「棚卸し＋共通方針」を1セッション：**

```
プロジェクト名：{project-name}
対象：サイト全体
改善タイプ：A レスポンシブ / B コード整理 / C 崩れ修正（複数可）
補足：{統一したいブレークポイント・整理の方針・気になる崩れなど}

Task: サイト全体のコード改善を開始します。
docs/workflow-edit.md の「サイト全体モード」を読んで進めてください。
まずステップ1（棚卸し）とステップ2（common 先行パス）を行い、
各ページの対応はステップ3で1ページずつ進めます。
```

**② その後、ページごとに上の「単ページ改善用」テンプレートを対象ページを差し替えて回す。**
